## Part 1: Answers to the 5 Official COEP Viva Learning-Outcome Checks

### Check 1: Why is modular exponentiation cheap but the discrete-log / factoring problem hard?
* **Why Modular Exponentiation ($a^b \pmod n$) is Cheap ($O(\log_2 b)$):**
  Using binary square-and-multiply (`pow_mod_with_trace` in `blockchain_lite/crypto/number_theory.py`), we decompose the exponent $b = \sum_{i=0}^{k-1} b_i 2^i$ where $k = \lfloor \log_2 b \rfloor + 1$. Instead of multiplying $a$ by itself $b$ times ($O(b)$), we repeatedly square the running base modulo $n$ ($k-1$ squarings) and multiply into the accumulator only when bit $b_i = 1$ (at most $k$ multiplications). Because we reduce modulo $n$ after every single multiplication, intermediate values never exceed $n^2$. For a 256-bit exponent, `pow_mod` requires only `272` modular operations ($< 2\text{ ms}$).
* **Why Factoring ($n = p \cdot q$) and Discrete Logarithm ($g^x \equiv y \pmod p$) are Hard (Sub-Exponential / Exponential):**
  Modular reduction (`% n`) folds the infinite integer line onto a finite ring $\mathbb{Z}_n$, destroying the monotonic magnitude information that allows binary search on real numbers ($a^x$ over $\mathbb{R}$ is easily inverted via $\log_a(y)$). No polynomial-time classical algorithm is known to invert multiplication of two large primes ($p, q$) or to invert modular exponentiation; the fastest known classical algorithm (General Number Field Sieve) runs in sub-exponential time $\exp\left(O((\ln n)^{1/3} (\ln \ln n)^{2/3})\right)$, creating the computational asymmetry that makes RSA and public-key signatures possible.

### Check 2: Change one byte of one transaction — trace exactly what breaks and why.
When 1 byte (or even 1 bit) of a transaction $T_j$ inside Block $B_k$ is modified (verified by `FullChainValidator.trace_tamper_cascade()`):
1. **Canonical Signing Preimage & RSA Signature Break (`Worklet 1.4`):** Modifying an output amount or recipient address changes `T_j.signing_preimage_bytes()`. By the avalanche property of SHA-256, the message representative $m_{\text{int}}'$ changes completely, so $S^e \pmod n = m_{\text{int}} \ne m_{\text{int}}'$, causing `T_j.verify_signatures()` to return `False` (`TamperDetectedError`).
2. **Transaction ID (`tx_id`) Breaks (`Worklet 2.4`):** `T_j.tx_id = SHA256(T_j.to_bytes())` flips $\approx 50\%$ of its 256 bits (`AvalancheReport`).
3. **Merkle Leaf, Branch Path & Merkle Root Break (`Worklet 2.2 & 2.3`):** The leaf hash `H(0x00 || tx_id)` changes, which alters every ancestor node `H(0x01 || left || right)` along the $\lceil \log_2 N \rceil$ path to the root. The recomputed Merkle root no longer matches `B_k.merkle_root` stored in Block $B_k$'s 88-byte header (`TamperDetectedError`).
4. **Block Header Hash & Proof-of-Work Break (`Worklet 2.1 & 2.5`):** If the attacker updates `B_k.merkle_root` in the header to match the tampered transaction, the 88-byte header changes. Consequently, `SHA256(B_k.header_bytes())` changes completely, invalidating the Proof-of-Work leading zero bits (`verify_block_pow` fails) and no longer matching `B_k.block_hash`.
5. **Downstream Predecessor-Hash Links Break (`Worklet 2.1 & 3.1`):** Even if the attacker re-mines a new PoW nonce for Block $B_k$ (producing `new_block_hash`), Block $B_{k+1}$ stores `B_{k+1}.previous_hash == old_block_hash != new_block_hash`. Every subsequent block $B_{k+1}, B_{k+2}, \dots, B_{\text{tip}}$ is invalidated unless the attacker re-mines the entire suffix of the blockchain faster than the honest network. Re-mining cannot be done cheaply: each block's `difficulty` must equal the value the consensus schedule derives from chain history (`ledger/consensus.py::expected_difficulty`), so a block that simply declares difficulty 0 is rejected (`tests/test_attack_scenarios.py::test_d1_*`).

### Check 3: What does a Merkle proof prove, and what is its size for $N$ transactions?
* **What it proves:** A Merkle inclusion proof (`MerkleProof`) cryptographically proves to a light client (holding only the 88-byte block header containing the 32-byte `merkle_root`) that a specific transaction `tx_id` was committed at position `tx_index` inside that block, without downloading all $N$ transactions in the block.
* **Size for $N$ transactions:** The proof contains `tx_id` (32B), `tx_index` (4B), `merkle_root` (32B), and exactly $\lceil \log_2 N \rceil$ sibling steps (each consisting of a 1-byte `LEFT`/`RIGHT` direction flag and a 32-byte `sibling_hash`, i.e., 33 bytes per step). Thus its asymptotic complexity and size are $\Theta(\log_2 N)$ hashes:
  * For $N = 8$ transactions: $\lceil \log_2 8 \rceil = 3$ sibling hashes ($99$ step bytes).
  * For $N = 1,000,000$ transactions: $\lceil \log_2 10^6 \rceil = 20$ sibling hashes ($660$ step bytes) instead of downloading hundreds of megabytes of transactions.

### Check 4: Why does the previous-hash link make the chain tamper-evident?
Each block $B_i$'s 88-byte header embeds `B_i.previous_hash = SHA256(B_{i-1}.header_bytes())`. Because SHA-256 is collision-resistant and preimage-resistant, `B_i.block_hash` is a recursive cryptographic commitment to $B_i$'s own transactions **and** to the entire history $B_0 \to B_1 \to \dots \to B_{i-1}$. Editing any byte in historical block $B_k$ ($k < i$) changes `B_k.block_hash`, which immediately causes a mismatch with `B_{k+1}.previous_hash`. If the attacker attempts to patch `B_{k+1}.previous_hash`, that changes `B_{k+1}.block_hash`, breaking `B_{k+2}.previous_hash` in a domino effect all the way to the chain tip.

### Check 5: Distinguish what a signature guarantees from what proof-of-work guarantees.
| Dimension | Digital Signature (RSA Private/Public Key) | Proof-of-Work (Nonce Search over Block Header) |
| :--- | :--- | :--- |
| **Mathematical Basis** | Trapdoor one-way permutation ($s = m^d \pmod n$, verified via $s^e \pmod n$) requiring secret knowledge of private key $d$. | Keyless brute-force preimage search finding a `nonce` such that `SHA256(header) < 2^(256 - D)`. Anyone can compute hashes; no secret key is involved. |
| **What It Guarantees** | **Authenticity, Ownership Authorization, Non-Repudiation & Payload Integrity:** Proves that the holder of the private key corresponding to `sender_pubkey` authorized spending a specific UTXO to specific outputs. | **Computational Cost, Sybil-Resistant Block Ordering & Fork Convergence:** Proves that expected $2^D$ hash operations were expended to seal a block at a specific position in history, making history rewrites expensive and enabling objective most-cumulative-work fork resolution (difficulty is checked against the schedule, so work cannot be self-declared). |
| **What It Does NOT Guarantee** | A signature alone does **not** prevent a wallet owner from signing two conflicting transactions spending the same UTXO (double-spending) or establish global transaction ordering. | Proof-of-Work alone does **not** authorize spending a user's UTXOs—a miner can mine a valid PoW nonce over a forged transaction, which will still be rejected by signature verification! |

## Part 2: Answers to the 15 Technical Viva Questions (+ 4 on the audit fixes)

1. **Why is fast modular exponentiation efficient?**
   Right-to-left binary square-and-multiply (`pow_mod_with_trace`) scans the $\lfloor \log_2 e \rfloor + 1$ bits of the exponent $e$, performing at most $2 \lfloor \log_2 e \rfloor + 1$ modular multiplications and reducing intermediate products modulo $m$ on every step so operands never exceed $m^2$. This reduces time complexity from exponential $O(e)$ to logarithmic $O(\log_2 e)$ in the value of $e$.
2. **What assumptions underlie RSA security?**
   RSA security rests on the **Integer Factorization Assumption** (given $n = p \cdot q$ for large random primes $p, q$, computing $p$ and $q$—and hence Carmichael's totient $\lambda(n) = \text{lcm}(p-1, q-1)$ and $d \equiv e^{-1} \pmod{\lambda(n)}$—is computationally infeasible) and the **RSA Trapdoor Permutation Assumption** (computing $e$-th roots modulo composite $n$ without knowing $d$, i.e., recovering $m$ from $m^e \pmod n$, is hard), combined with the collision/preimage resistance of SHA-256 used in the message representative.
3. **What is the difference between a private key and a password hash?**
   A **password hash** is a one-way digest `H(password || salt)` stored by a server to verify login attempts via equality comparison; anyone who steals the hash or intercepts the password can replay it, and it cannot sign arbitrary messages without exposing the secret. An **asymmetric private key** $d$ never leaves the client wallet and mathematically generates a unique, message-bound signature $s = m^d \pmod n$ for each transaction; the server verifies $s^e \equiv m \pmod n$ using only the public key $(n, e)$, so the secret is never transmitted or stored on the server.
4. **What exactly does the signature cover?**
   In `RSACryptoEngine.sign()` and `Transaction.signing_preimage_bytes()`, each input signature covers the domain tag `b"BCLT-RSA-SHA256-V1|"`, the signer's canonical `RSAPublicKey` bytes, and the transaction's unsigned binary preimage (`tx_type`, `timestamp`, all `TxInput` outpoints `(prev_tx_id, output_index, sender_pubkey)` with signatures omitted, and all `TxOutput` `(amount, recipient_address)` records).
5. **What happens when a signed transaction changes?**
   Changing even 1 bit of `tx_type`, `timestamp`, any input outpoint, or any output amount/recipient alters `signing_preimage_bytes()`, which flips $\approx 50\%$ of the bits in the SHA-256 digest inside `_encode_message_representative()`. During verification, $s^e \pmod n$ recovers the original representative $m_{\text{int}}$, which fails equality with the modified $m_{\text{int}}'$, raising `TamperDetectedError`.
6. **What does the transaction ID (`tx_id`) identify?**
   `tx_id = SHA256(tx.to_bytes())` is the 32-byte cryptographic digest of the **full canonically serialized transaction** (including all inputs, signatures, and outputs). It uniquely identifies that exact signed transaction in the `UTXOSet` outpoint map `(tx_id, output_index)`, the block's `MerkleTree` leaves, and the transaction history index.
7. **What does a Merkle proof establish?**
   A `MerkleProof` establishes that a specific transaction `tx_id` was included at leaf index `tx_index` in the ordered transaction list committed to by a block header's 32-byte `merkle_root`, using only $\lceil \log_2 N \rceil$ sibling hashes (`LEFT`/`RIGHT` steps) and domain-separated hashing (`0x00` leaf, `0x01` internal node) without requiring the light client to download the full block body.
8. **How does proof-of-work validate a candidate block?**
   `verify_block_pow(block)` serializes the block's 88-byte canonical header (`index`, `previous_hash`, `merkle_root`, `timestamp`, `difficulty`, `nonce`), computes `digest = SHA256(header_88_bytes)`, verifies `digest == block.block_hash`, and checks that the big-endian 256-bit integer value of `digest` is strictly less than the target threshold $T(D) = 2^{256 - D}$ (i.e., has at least $D$ leading zero bits).
9. **Why must chain validation start from genesis?**
   Whether a transaction input in Block $B_k$ is valid depends on whether its referenced `(prev_tx_id, output_index)` exists and remains unspent in the UTXO state accumulated from Block $B_0$ (Genesis) through $B_{k-1}$, and whether every ancestor block link `previous_hash` is unbroken. Validating only the tip block would allow an attacker to spend nonexistent or already-spent funds created in a forged earlier block.
10. **Why can a local ledger still be rewritten by a sufficiently capable attacker?**
    Cryptographic hashes and Proof-of-Work make tampering **detectable** and computationally **expensive**, not physically impossible. An attacker with write access to local disk storage who knows no external `expected_genesis_hash` is pinned can generate a new Genesis block, re-mine a replacement chain satisfying PoW difficulty $D$, and recompute the `.bclt` SHA-256 file seal. Defending against full-history replacement requires either pinning a trusted `expected_genesis_hash` out-of-band or replicating state across independent network peers.
11. **Why do balances derive from the selected valid chain?**
    Wallets do not store a mutable "account balance" integer; instead, a wallet's balance is the sum of `amount` across all unspent transaction outputs (`UTXOEntry`) locked to `wallet.address` in the `UTXOSet` constructed by replaying the currently authoritative valid chain from Genesis to tip.
12. **How can forks affect available balances?**
    When two competing valid branches diverge after Block $B_k$, a transfer confirmed only on Branch A creates UTXOs in Branch A's `UTXOSet` that do not exist on Branch B (and vice versa). If Branch B accumulates strictly more schedule-verified cumulative work ($\sum 2^{D_i}$) and wins `resolve_forks()`, the ledger atomically replaces its `UTXOSet` with Branch B's state, causing balances and spendable UTXOs to reflect Branch B's transaction history.
13. **What makes the most-work valid chain different from simply accepting the longest chain?**
    Accepting the "longest chain" without full validation allows an attacker to broadcast a long branch containing forged signatures, double-spends, inflated coinbase rewards, or unmined headers. Counting blocks is also wrong: before the audit fix, five difficulty-0 blocks (0.02 s of work) replaced two honest difficulty-12 blocks (13 s). `BlockchainLedger.resolve_forks` now runs `FullChainValidator.validate_chain()` from Genesis on every candidate (including the difficulty-schedule, timestamp and coinbase-height rules), disqualifies any branch with a single invalid block, and then picks the branch with strictly greater cumulative work; equal work keeps the active chain.
14. **What can the client-server architecture guarantee, and what remains trusted?**
    Because private keys stay strictly inside `Wallet` on the client side and the server explicitly rejects any RPC containing `private_key` fields (`THR-09`), even a compromised or malicious `TCPSocketLedgerServer` **cannot forge a user's RSA signature** to steal their UTXOs. However, in a single-server setup, the client still trusts the server for availability (not censoring transactions) and for serving the best chain. With `verify_transaction_inclusion_spv(..., trusted_genesis_hash=...)` the client verifies the header chain itself (links, PoW, scheduled difficulty, timestamps), so the server cannot fake a Merkle root cheaply; it still cannot detect a withheld heavier chain without other peers.
15. **Why is this project not automatically a decentralized or production-ready blockchain?**
    This project is an educational foundations-first system built on Python's standard library: (a) it uses 384/512-bit deterministic educational RSA rather than constant-time side-channel-hardened 2048-bit RSA-PSS or secp256k1 ECDSA; (b) it runs a single loopback TCP server rather than a decentralized peer-to-peer gossip network; (c) its pure-Python bitwise SHA-256 runs at $\sim 1,000\text{ H/s}$ for algorithmic clarity (the optional `--fast-hash` backend reaches $\sim 600{,}000\text{ H/s}$ with bit-identical results); and (d) the demo dashboard holds wallet keys server-side. See `SECURITY.md` for the full threat model.

16. **Why must the required difficulty come from chain history and not from the block header?**
    A header field is chosen by whoever mined the block. If validators trusted it, an attacker could declare difficulty 0, mine instantly and still be "valid" (audit defect D1). `consensus.expected_difficulty(blocks_so_far, params)` derives the required value from protocol parameters held by the validator (fixed difficulty, or the retarget rule over the last interval), and every block must match it exactly. The same principle applies to persisted files: a `.bclt` header whose difficulty or block reward disagrees with the protocol is rejected (D2).
17. **Why does the coinbase commit the block height?**
    A coinbase has no inputs, so two coinbases paying the same miner the same amount at the same timestamp would serialize identically and share a `tx_id`, colliding in the UTXO set (D3). Each non-genesis coinbase stores the block height in its `timestamp` field and the validator enforces `coinbase.timestamp == block.index`, so every coinbase is unique without changing the wire format (protocol version stays `1`).
18. **What timestamp rules does a block obey, and why?**
    A non-genesis block's timestamp must be at least the median of the previous 11 block timestamps and at most two hours ahead of the validator's clock. Without bounds an attacker could choose timestamps to steer difficulty retargeting (D8). Equal-to-median is allowed so several blocks mined in the same second remain valid.
19. **What does the anchored SPV check prove, and what does it not?**
    Given a trusted genesis hash, `WalletClient.fetch_verified_headers` proves the server's headers form a valid proof-of-work chain from that genesis under the consensus schedule, so the Merkle root used for the inclusion proof cannot be forged without real work. It does not prove the chain is the heaviest one: a server can still serve a correctly mined fork or withhold blocks (`tests/test_phase13_spv_and_keys.py::test_limitation_*`). Waiting for more confirmations narrows this.

## Part 4: Design Journal, Pitfall Mitigations & Audit Fixes

1. **Pitfall 1 (Slow or Broken Modular Exponentiation):** Mitigated in `number_theory.py` via iterative right-to-left binary square-and-multiply reducing modulo $m$ on every step, verified against 513-bit exponents and Mersenne prime $M_{521}$.
2. **Pitfall 2 (Merkle Tree Missing Swapped Transactions or Odd-Tail Spoofing — `F-003`):** Mitigated in `merkle.py` using domain-separated prefixes (`0x00` for leaves, `0x01` for internal nodes), binding `tx_index` parity (`idx % 2`) to `LEFT`/`RIGHT` sibling ordering, and rejecting odd right-child steps where `sibling_hash == current_hash`.
3. **Pitfall 3 (Treating `previous_hash` as Decoration):** Mitigated in `validator.py` (`FullChainValidator.validate_chain_or_raise`), which enforces `block[i].previous_hash == block[i-1].block_hash` and `block[i].verify_crystallized_integrity()` across every block from Genesis.
4. **Pitfall 4 (Confusing Signatures with Proof-of-Work):** Separated cleanly across `Worklet 1` (`RSACryptoEngine` + `Transaction.verify_signatures`) and `Worklet 2` (`ProofOfWorkMiner` + `verify_block_pow`), with both enforced independently during full-chain validation.
5. **Pitfall 5 (Reloading Persisted Chain Without Re-Validating — `F-001` & `F-005`):** Mitigated in `persistence.py` via crash-safe `<target>.tmp` + `fsync` + `os.replace()` writes, outer 32-byte SHA-256 seal checks, full Genesis-to-tip re-validation under the caller's protocol parameters (never the file header's), and optional `expected_genesis_hash` pinning.
